# 需求雷达：路线图

更新：2026-10-19。方案见 [`../docs/ideas/demand-radar.md`](../docs/ideas/demand-radar.md)，技术选型与实测记录见 [`../docs/ideas/demand-radar-tech.md`](../docs/ideas/demand-radar-tech.md)，同类项目调研见 [`docs/landscape.md`](docs/landscape.md)，市场调研见 [`docs/market.md`](docs/market.md)。

## 定位

同类项目（Reddit_Scrapper、pain-miner、sift 等）都在早期，没有一个同时做到：**全本地模型、一条命令部署、质量可量化**。这三点是我们的差异化，后续每一步都不能丢掉它们：不引入必须付费的 API，不增加部署步骤，每次改动都过评测。

## 现在在哪

已经能用：四类公开数据源 → 本地模型抽取 → MongoDB → Markdown 清单，`docker compose up` 一条命令部署，31 个离线测试。

质量有了可量化的基线：45 条人工标注的真实样本（`eval/eval_set.json`），`python -m demand_radar eval` 一键评测。qwen2.5:3b、温度 0 时 **F1 = 85.1%**（精确率 83.3%、召回率 87.0%），两次运行逐条结果完全一致。

还没做到的：每次只抓最新几条，没有历史回填；相似需求不会合并；只有 Markdown 没有看板；GitHub 源和本地真机部署没验证过。

## 技术路线

每一步结束都有一个能看到的结果；每次改动都先跑 `eval`，F1 下降就不合并。

### 第 1 步：调用模型前加规则预过滤（1–2 天）

**为什么先做它**：基线剩下的 4 条误报里，有 3 条根本不需要模型判断——2 条是 ProductHunt 的产品发布，1 条正文只有「submitted by /u/xxx」。用规则直接挡掉，准确度提高；被挡掉的每一条还省下一次 7–9 秒的模型调用，速度也一起提高。改动小、风险低，现有评测能马上验证。同类项目里星数最多的 Reddit_Scrapper 也是「先便宜地粗筛、再交给模型」，印证了这个方向。

- [ ] 正文为空、或只剩模板内容（`submitted by`、`[link] [comments]`）→ 丢弃
- [ ] 供给类内容 → 丢弃：标题以 `Show HN:` 开头的**帖子本身**、「I made / I built」类自我介绍、ProductHunt 来源
  - 只过滤帖子，不过滤帖子下的评论：评测集里 Audiomass 那条就是 Show HN 帖子下的一条真需求评论
- [ ] 机器人内容（正文是 JSON）、Reddit 搜索结果里混进来的版块简介 → 丢弃
- [ ] 评测时把预过滤一起算进去，同时报告「调用了多少次模型」

验收：评测 F1 提升，且没有任何「应入选」的样本被规则误杀。

### 第 2 步：并发调用模型（半天）

- [ ] 现在是逐条串行，改成同时发出多个请求（配合 Ollama 的 `OLLAMA_NUM_PARALLEL`）
- [ ] 在 GPU / Apple 芯片机器上提升明显；纯 CPU 上要实测，可能不明显

验收：同一评测集总耗时下降，F1 不变。

### 第 3 步：持续积累（1 周）

从「能跑一次」到「真正有用」的关键一步。

- [ ] **增量抓取**：每个源记录上次抓到哪里（时间或 id），下次只抓新的
- [ ] **历史回填**：softwarerecs 有 2.3 万条、HN 关键词能命中上万条，在各源限额内分批拉
- [ ] **实测 Arctic Shift 作为 Reddit 数据源**（pain-miner 在用）：如果公开可用、条款允许，能同时解决 Reddit RSS 的限流和没有历史数据的问题
- [ ] **相似需求合并**：
  - 用本地 embedding 模型把每条需求转成向量（`bge-m3` 支持中英文，或 `nomic-embed-text`），同样走 Ollama，不需要 key
  - 聚类方法参考 sift（embedding → UMAP 降维 → HDBSCAN）；数据少时先用简单的相似度阈值
  - 合并后热度 = 各条之和，并记录来自几个来源
  - 几千条的规模**不需要向量数据库**：向量存在 MongoDB，计算在内存里做
- [ ] **定时运行**：compose 里加一个每天跑一次的服务

验收：同一需求在不同来源出现，清单里只有一条，并标明来自几个地方、共多少人提过。

### 第 4 步：Web 看板（1 周）

- [ ] 后端 FastAPI，从 MongoDB 读，按领域、热度、时间筛选
- [ ] 前端一个静态页，不引入前端框架
- [ ] 放进 docker-compose，`docker compose up` 后打开浏览器即可
- [ ] 「已有方案」提示：查 Product Hunt、小众软件等供给源，标注「可能已有人做了」。GitHub 上有 290+★ 的 idea-validation 项目专做这件事，先评估能否直接集成
- [ ] 每周摘要：本周新增的高分需求导出一份 Markdown

验收：自己每周看一次看板，能挑出 1–2 个想做的点子。

### 第 5 步：开源发布（视前面进度）

- [ ] 拆成独立仓库，补英文 README、License、贡献指南
- [ ] CI 跑单元测试和评测集
- [ ] 第一个 Release，写清楚「它能做什么、不能做什么、数据从哪来、怎么合规」
- [ ] 发到 HN / V2EX / r/SomebodyMakeThis 收反馈
- [ ] 联系 pain-miner、sift 等同类项目的作者，看能否互相集成（例如他们用我们的评测方法，我们接入他们的数据源）

### 穿插进行：验证价值

同类项目都在「找出痛点」，但没有一个证明过清单真能帮人做出产品。这是整个方向最大的不确定性。

- [ ] 自己从清单里挑一个点子真正做出来，记录从发现到上线的过程，作为项目价值的第一个证据

### 穿插进行：真机验证

需要你在自己电脑上操作，我的沙箱复现不了普通电脑的环境（这里加了代理和证书）。可以在上面任意一步之间穿插。

- [ ] 原样执行 `docker compose up`，把第一次运行的问题贴给我修
- [ ] 验证 GitHub 源（沙箱只能访问当前仓库，GitHub 源只有单元测试）
- [ ] 看看在你机器上每条要几秒，决定默认模型

## 模型选择

测试阶段用 **qwen2.5:3b**：F1 85.1% 达到目标，模型约 1.9GB，8GB 内存可跑。

- [ ] 把 `docker-compose.yml` 的默认模型从 7b 改成 3b，降低配置要求
- [ ] 小模型对比（纯 CPU 沙箱，45 条评测）：

  | 模型 | 45 条耗时 | F1 |
  |---|---|---|
  | qwen2.5:3b | 390 秒 | 85.1% |
  | qwen2.5:1.5b | 198 秒 | 78.0% |
  | qwen2.5:0.5b、qwen3:1.7b、llama3.2:1b、gemma3:1b | 测试中 | |

  有比 3b 更快、F1 不低于 85% 的再换。

## 阶段 2 遗留（穿插处理）

- [x] 评测集扩充到 45 条，覆盖各源和各类错误
- [x] `eval` 命令：准确率、精确率、召回率、F1
- [x] 抽取温度设为 0，结果可复现
- [x] 限制模型输出长度、设置请求超时，防止小模型失控卡住整批
- [ ] **可信度要有区分度**（优先）：现在几乎都是 0.9。参考 Reddit_Scrapper 分项打分（痛点清晰度、情绪强度、可实现性），参考 pain-miner 不只给一个黑盒分数、同时列出证据
- [ ] **清单附一句原文摘录**（优先）：方便人工核对模型有没有概括偏，也是 pain-miner「给证据」的做法
- [ ] 输出语言统一：要么全中文，要么保留原文语言
