## 定位

开源、自托管的需求发现工具。同类项目（Reddit_Scrapper、pain-miner、sift 等）都在早期，没有一个同时做到：**全本地模型、一条命令部署、质量可量化**。这三点是我们的差异化，后续每一步都不能丢：不引入必须付费的 API，不增加部署步骤，每次改动都过评测。

市场调研的结论是需求真实、商业天花板有限，所以**先做出能发布的版本拿到真实反馈，再做重功能**。

## 现在在哪

v0.1 功能已全部完成：四类公开数据源 → 规则预过滤 → 本地模型抽取 → 有害规则标记 → MongoDB → 排序 → 清单 / 周报（中英文），`docker compose up` 一条命令部署。v0.2（增量抓取、运行记录、并发抽取、历史回填、定时运行、Arctic Shift 源）和 v0.3 的两项（相似需求合并、Web 看板）已于 2026-10-20 合并进主线并在 Mac（M5）上逐项真机验证；222 个离线测试，CI 通过。

质量（2026-10-20，116 条标注样本，Mac GPU 上 Qwen3-4B-Instruct-2507，温度 0）：

| 输出语言 | F1 | 有害需求进清单 | 正常需求被转人工 |
|---|---|---|---|
| 中文 | **92.4%** | 0 / 10 | 0 |
| 英文 | **90.9%** | 0 / 10 | 0 |

比 61 条时的 96.8% 低，是新样本更难（GitHub 那批要区分「平台功能请求」和「给开源项目提的请求」），不是退步；仍高于 85.1% 的验收线。相似需求合并在 23 对标注上准确率 82.6%（精确率 100%、召回 63.6%）。

| 输出语言 | F1 | 精确率 | 召回率 | 有害需求进清单 | 正常需求被转人工 | 规则误杀 | 61 条耗时（沙箱 CPU） |

## 里程碑

### v0.1：可以发布（约 1.5 周）

拿得出手，能放到社区让人试用，并能每周产出有价值的内容。

- [x] 规则预过滤：空帖、作品发布帖、机器人内容等不再交给模型（评测集里挡掉 10 条，零误杀）
- [x] 分项打分：痛点清晰度、表达强度、可实现性
- [x] 原文摘录：程序从原帖挑一句最像需求的原话（模型抄写时约 29% 被翻译或改写，改由程序挑）
- [x] 输出语言可配置：中文 / 英文，两种语言各一份完整提示词
- [x] 抽取失败也记录，超过 3 次不再重试
- [x] 综合排序：分项打分 + 热度
- [x] 每周摘要命令 `digest`
- [x] 有害需求（追踪、监视、曝光、骚扰、欺骗特定的人）不进正文，转「待人工确认」区
- [x] 默认模型 3b；MIT 协议；英文 README；CI
- [x] `local/<模型>`：接任意 OpenAI 兼容的本地服务（mlx-lm、LM Studio、llama.cpp）
- [ ] 拆成独立仓库（等你定名字）

验收：评测 F1 ≥ 85.1% ✓（qwen2.5:3b 时英文 89.7%、中文 83.6% 差 1 条；换成 Qwen3-4B 后 116 条评测集中文 92.4%、英文 90.9%，容器默认的同一模型 61 条上 95.2% / 96.8%），摘录全部是原文原话 ✓，规则零误杀 ✓，有害需求进清单 0 条 ✓；Mac 上 `docker compose up` 能出清单和摘要 ✓。

**发布后**：发到 HN、r/SaaS、Indie Hackers、V2EX，收集反馈，再决定 v0.2 的优先级。

### v0.2：持续积累（约 1.5 周）

跑一个月后，库里是几千条有效需求，而不是每天重复处理同样的内容。

- [x] 评测集扩到 100 条以上（中文 F1 离验收线只差 1 条，样本太少分不清改进和噪声）——2026-10-19 扩到 **116 条**（101 条真实 + 15 条构造）：softwarerecs 21、HN 22、GitHub 16（此前为 0，区分「对平台产品提的功能请求只能平台方做」与「给开源项目提的请求个人可贡献」）、Reddit 39、Product Hunt 3；按类型应入选 56、需求但做不了 15、可做性存疑 10、非需求 25、有害 10。新样本全部用项目自身数据源代码抓取并经 `clean()`，原始数据未入库。2026-10-20 在新集上重跑：Qwen3-4B 中文 F1 92.4%、英文 90.9%，有害需求进清单 0 条
- [x] 增量抓取：每个源记录上次抓到哪
- [x] 历史回填：softwarerecs 有 2.3 万条、HN 关键词能命中上万条，分批拉，可中断续跑（`backfill --source … --pages N`）
- [x] 并发调用模型（`--workers`，默认 2；纯 CPU + Ollama 默认串行时提升有限，待真机实测）
- [x] 运行记录：每次运行的抓取数、过滤数、失败数、耗时
- [x] 定时运行：每天抓取，每周出摘要（compose 里可选的 `scheduler` 服务，`--profile cron`）
- [x] 实测 Arctic Shift 作为 Reddit 数据源：公开无 key、30 次实测无 429、能按时间增量和回填，已接入为 `arctic_shift` 源；但服务端关键词搜索超时（改本地筛）、新帖 score 要 36 小时后才准、第三方免费服务无可用性承诺且条款是灰色地带，所以 RSS 保留兜底、合规由你判断（见 [docs/arctic-shift.md](docs/arctic-shift.md)）

验收：连续运行一周不重复处理；回填能中断续跑。

### v0.3：合并与看板（约 2 周）

- [x] 相似需求合并：本地 embedding 模型向量化（走 `/v1/embeddings`），余弦相似度阈值增量归簇，`cluster` 命令 / `run --cluster`；清单和周报每簇只列代表，标来源数和条数；23 对标注样本 + `cluster --eval` 评测合并准确率。2026-10-20 真机实测：`nomic-embed-text` 不懂中文（43.5%，中文 16 对只对 5 对），`qwen3-embedding:0.6b` 与 `bge-m3` 在各自最佳阈值下都是 87.0%（23 对里错 3 对），默认改为前者、阈值 0.78。标注对太少，阈值待更多真实数据复核；不够再上 UMAP + HDBSCAN
- [x] Web 看板：FastAPI + 静态页，按领域、时间、来源、关键词筛选，按排序分 / 热度 / 时间排；另有待人工确认、运行记录两页；compose 里可选的 `web` 服务（`--profile web`）
- [ ] 「已有方案」提示：优先评估集成现有的 idea-validation 开源项目

验收：同一需求在多个来源出现只显示一条，标明来源数和总热度。——清单、周报、看板都已做到 ✓（2026-10-20 看板补上按簇折叠，代表和排序分与清单共用 `cluster.group`；三处都标来源数、条数和总热度，总热度为 0 时不写）。真实库 47 条里只合出 1 对，数据多了再看效果

## 模型选择

容器默认 **`qwen3:4b-instruct-2507-q4_K_M`**（2026-10-20 起，Apache-2.0；容器 CPU 上 61 条评测中文 95.2%、英文 96.8%，每条约 7 秒）。下面是最初 45 条评测时的对比留档，当时默认 qwen2.5:3b：

| 模型 | 45 条耗时 | F1 | 结论 |
|---|---|---|---|
| qwen2.5:3b | 390 秒 | 85.1% | 默认 |
| qwen2.5:1.5b | 198 秒 | 78.0% | 低配机器备选 |
| qwen2.5:0.5b | 103 秒 | 0% | 不可用 |
| qwen3:1.7b | 每条 30 多秒 | — | 默认开启思考模式，比 3b 还慢，不推荐 |
| llama3.2:1b、gemma3:1b | 未测完 | — | 中文弱，优先级低 |

上表是 45 条时、容器 CPU 的数据。v0.1 的 61 条结果见「现在在哪」。

**Mac 上的推荐（2026-10-19 实测）**：mlx-lm 原生跑 **Qwen3-4B-Instruct-2507-4bit**，61 条评测集中英文 F1 均 96.8%，每条约 3 秒，Apache-2.0。详见 [`docs/model-selection.md`](docs/model-selection.md)。
