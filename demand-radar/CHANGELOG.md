# 更新记录

## 未发布

### 给 agent 用：语义检索和 MCP 服务（只读）

- **`search` 命令**：用一句话在已入库的需求里找最像的。向量就是 `cluster` 已经存在 `demands.embedding` 里的那份，内存里暴力算余弦，**不引入向量数据库**；同一簇只留最像的一条；只在 `embedding_model` 相同的文档里找；待人工确认区永远不返回。检索不写库、不替没有向量的需求补向量，而是在结果里提示还有几条没向量。
- **`mcp` 命令**：stdio 的 MCP 服务，给 Claude Code 等 agent 用，三个工具 `search_demands` / `get_demand` / `list_top`。自己实现最小的 JSON-RPC，不引入 `mcp` SDK，没有新依赖。stdout 只写协议消息，日志走 stderr。接法见 README「给 agent 用」。
- **相关度标签**：较相关（≥0.7）、弱相关（0.55–0.7）、疑似无关（<0.55），默认过滤 0.5 以下。在 47 条真实数据、5 条查询上量过：有真正匹配时排第 1、分数 0.72–0.91；没有匹配时最高 0.55–0.58；**泛泛的短查询会把沾边的打到 0.7 以上（实测 0.706），所以标签叫「较相关」并在工具说明里要求 agent 读内容确认**。样本很小，数据多了要重新量。
- **试过没采用：Qwen3-Embedding 的查询指令前缀**。5 条查询上排名没有改善，只是把分数整体压低。
- **注意**：默认的定时任务 `DR_CLUSTER=0`，不会生成向量，所以新入库的需求搜不到，要 `run --cluster`（`DR_CLUSTER=1`）或手动跑 `cluster`。

### 数据源由用户自己选：按风险分档，灰色来源默认关闭

- **每个源标风险档**（`sources.PROVIDERS`）：`open` 官方公开接口、`terms` 有条款要遵守、`gray` 官方不允许 / 不鼓励或来源是第三方归档、`varies` 看订阅哪个站点。这是我们对条款的理解，不是法律意见。
- **灰色来源默认全关**：`arctic_shift`、`appstore`、`googleplay`，以及自带的 Reddit RSS 订阅和 V2EX 订阅。默认只开 `softwarerecs`、`hn_algolia`、`bluesky`、`github`。有测试保证以后新加的灰色源不会被默认打开。**撤销了上一条「恢复 Reddit」的默认开启**：Reddit 想用请自己在 `sources.toml` 里打开。
- **RSS 每个订阅有自己的 `enabled` 开关**；订阅全关等于整个 rss 源关闭。
- **新命令 `demand-radar sources`**：列出每个源是否启用、风险档、条款链接和每个 RSS 订阅的开关。
- **开了灰色源会提醒**：每次 `run` 开始时，对用到的灰色 / 看订阅的源各打一行提示（写到 stderr），说明是谁开的、去读哪份条款。
- **升级**：如果你以前依赖默认抓 Reddit，升级后需要自己把 `[arctic_shift]` 的 `enabled` 改回 `true`。`dr-weekly` 这类挂载了 `sources.toml` 的容器，下次运行就会按新配置跑（新代码要重建镜像）。

### 数据源：Bluesky、V2EX，恢复 Reddit

- **`bluesky`（新）**：官方公开搜索接口，未登录，按短语（`is there an app`、`is there a tool`、`i wish there was an app`）搜最新帖子。调研里浓度最高（约 8/29），但量小，每周约 14 条。帖子没有标题，用正文开头当标题；热度取点赞数；作者信息不入库（链接里的 handle 只为能打开原帖）。只有 `api.bsky.app` 未登录可用，且翻页会 403，所以只取第一页；有游标时用 `since` 只要新的。真机试抓：3 个短语共 28 条。
- **RSS 每个订阅可单独设 `limit`**，覆盖全局 `--limit`。V2EX 这类每天几十帖的订阅，全局取 10 条会漏掉大半。
- **V2EX「问与答」**（中文）：`[[rss]] name = "v2ex/qna"`，`limit = 50`，公开 Atom feed。调研抽样约 5/30 是需求。V2EX 的条款页当时打不开（403），没读到原文；只读公开 feed，每天一次。真机试抓 50 条。
- **恢复 Reddit**：`arctic_shift` 开启，四个 Reddit RSS 订阅取消注释。一周验收已结束。Reddit 的条款仍是灰色地带，见 `docs/arctic-shift.md`。
- **没接**：Mastodon（社区普遍反感被抓取）、Product Hunt、Indie Hackers 等，见调研文档。

### 数据源：HN 加 Ask HN 和两个短语

依据 `docs/research/2026-10-28-data-sources.md`（在分支 `worktree-agent-aee21136855d97d40`，未合并）。

- **Ask HN 模式**：`sources.toml` 里写 `[hn_algolia.ask_hn]` 即开启，删掉这个表就关。每周约 240 个 Ask HN 帖、浓度低（抽样约 3/30 是需求），所以抓回来先在本地按整词关键词筛，再交给模型。游标按筛之前的结果推进，被筛掉的帖子不会下次再拉。一次最多取 100 帖，不受 `--limit` 影响。真机试抓一次：100 帖留下 10 条。
- **两个新短语**：`wish someone would`（抽样约 5/30）、`does anyone know of`。调研里 `alternative to` 抽样 0/30，没有加。
- **不支持回填**：Ask HN 目前只做增量，`backfill` 仍只回填短语查询。
- **升级**：`sources.toml` 是挂载进容器的，但 Ask HN 的抓取是新代码，要重建镜像才生效。第一次运行会取最近约 100 帖（约 3 天），之后每次只取新的。

### 排序分两个榜

- **问题**：热度信号实际上只有 GitHub 有（HN 评论、softwarerecs、Reddit 新帖基本是 0），而排序里热度项是 `log1p(热度)`：一个 1500 赞的 issue 加 7.3 分，分项打分每差一档才 1–1.5 分。一周验收（10-20～10-27）的清单前 12 名全是 GitHub，而且多是给 VSCode、terraform 提的功能请求，不是「还不存在的新产品」。
- **分榜**：来源是 `github`（或 `github/…`）的进「功能请求榜」，其余进「愿望榜」。清单、周报、看板分开展示，排序分只在同一榜内比较。愿望榜在前；库里只有一个榜的内容时，清单和周报与以前一字不差。功能请求榜在愿望榜之后、待人工确认之前，单独编号。
- **热度权重按榜取**：功能请求榜仍用 `heat`（默认 1.0）；愿望榜用新增的 `heat_wish`（默认 0.3），主要靠分项打分和簇的大小。两个都在 `sources.toml` 的 `[ranking]` 里。**升级后愿望榜里的排序分会变**（热度项缩小），旧的 `out/` 文件重新生成即可，数据库不用动。
- **簇**：簇里只要有一条愿望，整簇进愿望榜，代表也优先从愿望成员里选，GitHub 那条的热度分不会抢走代表。
- **看板**：新增「榜单」下拉框，默认看愿望榜，可切到功能请求榜或全部；接口 `/api/demands`、`/api/held`、`/api/domains`、`/api/sources` 新增 `board=wish|project` 参数，需求条目多一个 `board` 字段。
- **没做**：分榜按来源判断，不看内容，所以 HN 上有人提「给某某项目加个功能」仍算愿望。要按内容分得让抽取多输出一个字段，要改提示词并重跑评测，等有需要再做。

### 按本机配置推荐模型

- **`recommend` 命令**：检测内存、CPU、Apple 芯片、NVIDIA 显存，按档位表 `models.toml` 推荐抽取模型和嵌入模型，给出运行步骤和要写进 `.env` 的配置；`--write-env` 直接写入。在 Docker 里看不到 Mac 的 GPU，用 `--apple --ram-gb` / `--vram-gb` 指定。
- **模型可配置**：`docker-compose.yml` 的抽取模型改由 `.env` 里的 `DR_MODEL` 覆盖（默认不变），新增 `DR_EMBED_BASE_URL` 透传；新增 `docker-compose.nvidia.yml`，让容器里的 Ollama 用 NVIDIA GPU。
- **按出品地过滤**：档位表标出每个模型的出品地，`--exclude-origin cn` 改推非中国模型（Ministral 3、Gemma 4、EmbeddingGemma 等）。这些档位还没实测，见 `docs/research/2026-10-20-non-chinese-models.md`。
- **Google 低配模型实测**：Gemma 4 E2B（Mac GPU）帖子 F1 中文 85.5% / 英文 84.8%、评论中文 54.7%，而且要求中文时仍输出英文，不推荐；EmbeddingGemma 2（303MB）阈值调到 0.83 时合并 F1 83.3%、精确率 76.9%，可作非中国档位的嵌入模型。档位新增 `cluster_threshold`，`recommend` 写进 `DR_CLUSTER_THRESHOLD`。
- **兼容把 JSON 包进代码块的模型**：Gemma 4 在 JSON 模式下仍输出 ```json … ```，解析前去掉外壳，没有外壳的输出不受影响。
- **补测**：Qwen3.5-9B（Mac GPU）帖子 F1 中文 93.9% / 英文 91.1%、评论中文 78.4%，和 Qwen3-4B 差不多但慢一倍多，没有换；嵌入模型 qwen3-embedding 4b / 8b 合并 F1 84.2%，0.6b 是 77.8%，默认仍用 0.6b（体积小 4–8 倍）。

### 新数据源：应用商店低分评论（默认关闭）

- **`appstore`**：App Store 上指定 app 的 1–3 星评论，走苹果的评论 RSS，不加任何依赖。接口经常返回空结果，这时换格式只再试一次，还是空就跳过、不推进游标。
- **`googleplay`**：Google Play 上指定 app 的 1–3 星评论。自己实现了 Play 网页用的评论接口，没有引入 google-play-scraper：那个库一导入就会关掉整个进程的 HTTPS 证书校验。包名写错时直接报错，不会悄悄返回空。
- **默认关闭**：两个商店的条款和 robots.txt 都不鼓励自动抓取，开启前请读 `docs/research/2026-10-20-app-store-reviews.md` 第五节。在 `sources.toml` 里列出要看的 app 即可。
- **限速**：两个商店都是同域名至少隔 5 秒；每个 app 每轮最多翻 `max_pages` 页，翻到上次看过的评论就停。Google Play 被限流时整个域名冷却 60 秒，本轮剩下的 app 不再请求。
- **评论专用的抽取**：评论用单独的提示词，问的是「做个替代品、插件或配套工具能不能解决」。中文短评的正文长度门槛从 20 字放宽到 6 字，只对评论生效，帖子的规则不变。评论人昵称不入库。
- **评测**：新增 `eval/review_set.json`，150 条人工标注的低分评论，用 `eval --eval-set eval/review_set.json` 单独评测，不混进帖子的 F1。

评测（2026-10-20，Mac GPU 上 Qwen3-4B-Instruct-2507，温度 0）：

| 评测集 | 输出语言 | 改动前 | 改动后 |
|---|---|---|---|
| 评论 150 条 | 中文 | F1 9.1%（召回 4.9%） | **F1 80.6%**（精确率 69.3%、召回 96.3%） |
| 评论 150 条 | 英文 | — | **F1 83.2%**（精确率 84.8%、召回 81.7%） |
| 帖子 116 条 | 中文 | F1 92.4% | F1 92.4%（不变） |
| 帖子 116 条 | 英文 | F1 90.9% | F1 90.9%（不变） |

两个评测集上规则误杀都是 0，有害需求进清单都是 0。评论中文的误报主要是 bug 报告被当成痛点（35 条误报里 20 条）。试过在提示词里把「报 bug 不算」写得更细，中文只到 80.8%，英文降到 77.4%，没有采用。评论里有 1 条正常差评提到 fake reviews，被有害规则转去人工确认，按设计不改。

已知限制：`--limit` 对评论源的含义是「凑够这么多条就不再往后翻页」，已取回的一页都保留，首轮实际条数会多于 `--limit`。单条评论不按 app 聚合，同一个 app 的同类抱怨会各自成一条，交给相似需求合并（`--cluster`）去合；合并阈值 0.78 是在长帖上定的，短评上没有单独评测。

## v1.0.0（2026-10-20）

第一个发行版本。功能与 v0.3.0 相同，这一版做的是安装、部署和工程质量上的整理：可以 pip 安装、依赖版本锁定、容器更安全、CI 更完整。抽取逻辑和提示词没有改，抽取质量与 v0.3.0 相同。项目继续放在 `see` 仓库的 `demand-radar/` 目录下。

### 安装与打包

- **可以 pip 安装**：新增 `pyproject.toml`，装好后有 `demand-radar` 命令，和 `python -m demand_radar` 等价。看板依赖放在 `[web]` 可选依赖里。
- **默认配置随包分发**：`sources.toml` 和两份评测集打进安装包。在仓库外运行时，当前目录没有这些文件就用包里自带的。
- **锁定依赖版本**：`requirements.lock` 记录精确版本，Docker 镜像和 CI 都按它安装。`requirements.txt` 和 `requirements-dev.txt` 已删除，依赖声明统一放在 `pyproject.toml`。
- **新增 `--version`**。

### Docker

- **非 root 运行**：容器改用普通用户（uid 1000）运行。Linux 上 `./out` 没有写权限时，入口脚本会直接给出修法。
- **共用一个镜像**：app、scheduler、web 共用镜像 `demand-radar:local`，构建一次三个服务都更新。
- **看板只对本机开放**：看板没有登录，端口只绑 127.0.0.1，并加了健康检查。
- **固定 Ollama 版本**：Ollama 镜像固定为 0.40.6，不再用 `latest`。
- **抓取条数可配**：每轮抓取条数可以用 `DR_LIMIT` 环境变量设置。

### 抓取

- **配置报错更友好**：配置文件找不到或格式错时，给一句话提示，不再抛异常堆栈。

### 从 v0.3.0 升级

- **Linux 用户要改一次 `./out` 的属主**。v0.3.0 的容器以 root 运行，`./out` 里已有的清单和周报属于 root，新版本以 uid 1000 运行时覆盖不了。入口脚本会在开跑前检查并提示，按提示在 `demand-radar` 目录执行 `sudo chown -R 1000:1000 out` 即可。macOS 和 Windows 的 Docker Desktop 不受影响。
- **镜像要重建一次**：app、scheduler、web 改用同一个镜像名，执行 `docker compose build app`，再重启在跑的 scheduler、web。
- **看板地址不变**，但只对本机开放。局域网访问的改法见 README「常见问题」。
- 数据库结构没有变化，已有数据照常使用。

### 质量

- **代码检查**：接入 ruff，并修复了检查出的问题。
- **相似需求合并的隐患**：嵌入服务少返回向量时，以前会悄悄跳过那几条，现在会直接报错。
- **CI**：增加代码检查、Python 3.11 / 3.12 双版本测试、打包后在仓库外安装试跑、镜像运行检查。
- **贡献指南**：新增 `CONTRIBUTING.md`，写明开发环境、怎么加数据源、改动要过的检查。
- **架构图**：按 v1.0.0 重画，见 [`docs/architecture.md`](docs/architecture.md)。

## v0.3.0（2026-10-20）

第一个正式版本。路线图 v0.1 到 v0.3 的功能都已完成，并在 Mac（M5）上逐项真机验证。

### 能做什么

- **抓取**：五类公开数据源。
  - StackExchange softwarerecs
  - Hacker News（Algolia 搜索）
  - GitHub 功能请求 issue
  - Reddit，走 Arctic Shift 归档
  - 任意 RSS / Atom 订阅
- **增量和回填**：日常抓取按游标增量进行。历史回填可以中断，下次从断点续跑。
- **限速**：所有请求统一限速，按域名控制最小间隔，被限流时整个域名一起冷却。
- **抽取**：本地模型把帖子抽取成结构化需求，包括是不是需求、个人能否做成、清晰度、迫切度、可实现性。抽取前先过规则预过滤。原文摘录由程序从原帖里挑，不让模型抄写。
- **安全**：有害需求由规则标记，不进正文，转到「待人工确认」区。有害指追踪、监视、曝光、骚扰或欺骗特定的人。
- **排序与合并**：三项打分加权，再加上原帖热度。相似需求用本地嵌入模型合并：同一需求只显示一条，标明来源数、条数和总热度。
- **输出**：
  - 全量清单 `out/demands.md`
  - 每周摘要
  - Web 看板，可按领域、时间、来源、关键词筛选
  - 中英文两种输出
- **部署**：`docker compose up` 一条命令。可选常驻的定时服务和看板。Mac 上可以用 mlx-lm 调 Apple GPU。
- **评测**：抽取质量有 116 条标注样本，相似需求合并有 23 对标注，都可以用命令跑出数字。

### 质量

| 项目 | 结果 |
|---|---|
| 抽取 F1，中文（116 条，Qwen3-4B，Mac GPU） | 92.4% |
| 抽取 F1，英文（同上） | 90.9% |
| 有害需求进入清单 | 0 / 10 |
| 正常需求被误转人工 | 0 |
| 相似需求合并准确率（23 对） | 82.6%，精确率 100% |
| 容器 CPU 默认模型（61 条） | 中文 95.2%，英文 96.8% |

### 默认模型

- **抽取**：`qwen3:4b-instruct-2507-q4_K_M`，Apache-2.0，约 2.5GB，8GB 内存可跑，容器 CPU 上每条约 7 秒。
- **嵌入**：`qwen3-embedding:0.6b`，Apache-2.0，约 640MB。
- **Mac GPU**：`mlx-community/Qwen3-4B-Instruct-2507-4bit`，每条约 3 秒。

### 已知限制

- **Reddit 的条款**：Arctic Shift 和 RSS 两条路线的条款问题还没有定论，详见 [`docs/arctic-shift.md`](docs/arctic-shift.md) 第四节。正式使用前请自行判断。
- **相似需求合并**：标注只有 23 对。阈值 0.78 需要用更多真实数据复核。
- **RSS 订阅**：没有热度信息，排序会靠后。不支持需要登录的订阅。
- **私域数据**：还不能直接导入 CSV、JSON 这类导出文件，私域内容和公开内容也没有区分标记。
- **验收进行中**：v0.2「连续运行一周不重复处理」正在跑，2026-10-27 出结果。
- **未完成**：「已有方案」提示只做了调研，功能还没写，见 [`docs/research/2026-10-20-existing-solutions.md`](docs/research/2026-10-20-existing-solutions.md)。

这是第一个版本，没有升级步骤。以后的版本如果改了数据结构，会在这里写明迁移方法。
