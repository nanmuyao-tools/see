# 模型选型：在 Mac 上兼顾速度和质量

调研时间：2026-10-19。目标机器：Apple M5（基础款）、32GB 内存。任务是从社区帖子里抽取结构化需求（JSON），中英文都要处理。本文件给出候选、估算和测试计划；**最终以 `eval` 的 F1 和每条耗时为准**，估算只用来缩小范围。

## 一、现状和瓶颈

| 方案 | 每条耗时（实测） | 说明 |
|---|---|---|
| 沙箱，纯 CPU，qwen2.5:3b | 7–9 秒 | 之前的开发环境 |
| M5，Docker 里的 Ollama，qwen2.5:3b | 4–6 秒 | 真机验证实测；99 条共 10 分钟 |

**Docker Desktop 在 Mac 上不能把 Apple GPU 交给容器**，所以容器里的模型只能用 CPU。要用 GPU，模型得在 macOS 上原生运行。机器上已经装好 `mlx-lm`（Apple 自己的推理框架，直接用 GPU），它自带 OpenAI 兼容的 HTTP 服务（`mlx_lm.server`）。

## 二、为什么速度主要看模型体积

Apple 的 MLX 团队说明过：生成每个 token 的速度受内存带宽限制，而不是算力。M5 基础款带宽 153 GB/s（M4 是 120）。每生成一个 token 要把整个模型权重读一遍，所以：

> 生成速度（token/秒）≈ 带宽 ÷ 模型体积，再打个折扣

来源：[Apple MLX on M5](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)。

## 三、候选模型

全部来自 HuggingFace 的 `mlx-community`（MLX 格式，4-bit 量化），体积和参数量是从模型仓库实际读出来的；速度是按上面的公式估算的，**没实测**。

| 模型 | 体积 | 参数 | 估算生成速度 | 估算每条耗时 | 中文 | 协议 | 评价 |
|---|---|---|---|---|---|---|---|
| Qwen2.5-3B-Instruct-4bit | 1.7GB | 3.1B | ~60 tok/s | ~2–3 秒 | 好 | 非 Apache | 和现在容器里跑的是同一个模型，用来对照 GPU 带来的加速 |
| **Qwen3-4B-Instruct-2507-4bit** | 2.3GB | 4.0B | ~45 tok/s | ~3–4 秒 | 好 | Apache-2.0 | 社区下载量最高的 4B；**2507 版是纯指令版，没有思考模式**，适合输出 JSON |
| **Qwen2.5-7B-Instruct-4bit** | 4.3GB | 7.6B | ~25 tok/s | ~5–7 秒 | 好 | Apache-2.0 | 和现在的 3b 同一系列，提示词不用重调；质量明显高一档 |
| Qwen3-8B-4bit | 4.6GB | 8.2B | ~23 tok/s | ~6–8 秒 | 好 | Apache-2.0 | 更新一代，但默认开思考模式，要想办法关掉，有风险 |
| Qwen3.8-27B-4bit（机器上已有） | 16.1GB | 27.4B | ~7 tok/s | ~20–30 秒 | 好 | Apache-2.0 | 质量最好，但太慢，只适合做「二次复核」 |

估算每条耗时按「提示词约 700 token + 输出约 150 token」算，含首个 token 的延迟。

## 四、排除的候选和原因

| 模型 | 为什么不选 |
|---|---|
| Qwen3.8 官方小模型 | **不存在**。Qwen3.8 开放权重只有 27B、Flash-Next（177B MoE，111GB）和 2.4T 旗舰 |
| empero-ai/Qwen3.8-4B-Distill（第三方蒸馏，22 万下载） | 思考模式**永远开着**、关不掉，每条都要先生成一大段思考，和之前 qwen3:1.7b 一样会把输出额度耗光；模型卡只标了英文；自报的 gsm8k 分数比蒸馏前还低；需要特殊的注意力内核，MLX 下能否正常跑不确定 |
| Gemma 4 | MLX 社区最小的是 12B，没有 4B 版本 |
| Gemma 3 4B | 带视觉的多模态结构，体积偏大（3.4GB），协议非 Apache，中文弱于 Qwen |
| Llama 3.2 3B、Phi-4-mini | 中文能力弱，我们的数据源一半是中文输出 |

## 五、推荐和测试计划

**推荐先测两个：Qwen3-4B-Instruct-2507（速度型）和 Qwen2.5-7B-Instruct（质量型）**，加上 Qwen2.5-3B 做对照，三个共约 8GB。

测试方法，和之前选 3b 时一样，用评测集说话：

1. `mlx_lm.server --model <模型> --port 8080`（原生运行，用 GPU）
2. `python -m demand_radar eval --provider local/<模型> --base-url http://localhost:8080/v1`（中英文各一遍，加 `--lang en`）
3. 记录 F1、有害需求进清单条数、每条耗时，填进下表。基线是 v0.1 在 61 条评测集上的结果；摘录已改由程序挑选，不再随模型变化

| 模型 | 运行方式 | F1（中） | F1（英） | 有害需求进清单 | 61 条耗时 | 每条耗时 |
|---|---|---|---|---|---|---|
| Qwen2.5-3B（基线） | Docker 容器，CPU | 83.6% | 89.7% | 0 | 709 秒 / 591 秒（沙箱 CPU） | M5 CPU 上 4–6 秒 |
| **Qwen3-4B-Instruct-2507-4bit** | mlx-lm 原生，M5 GPU | **96.8%** | **96.8%** | 0 | 154 秒 / 150 秒 | **约 3 秒**（51 次模型调用） |
| Qwen2.5-3B（MLX GPU 对照） | — | 未测 | 未测 | | | 4B 已远超目标，省略 |
| Qwen2.5-7B-Instruct | — | 未测 | 未测 | | | 同上 |

基线数字来自云端会话在同一个 61 条评测集上的 v0.1 验收。两个模型的规则过滤都是 10 条、零误杀。

选择标准：F1 不低于基线的前提下，取最快的；如果 7B 的 F1 高出 5 个百分点以上，速度又在 6 秒以内，优先 7B。

## 六、顺带的架构建议

- **两段式**：日常用小模型跑全量，每周用 27B 复核进入清单的几十条，纠正小模型的误判。27B 一条 20 多秒，几十条也就十几分钟。放进 v0.2 之后考虑。
- **代码要改一处**（已完成）：加了 `local/<模型>` 前缀 + `--base-url`，能连任何 OpenAI 兼容的本地服务（mlx-lm、LM Studio、llama.cpp 都是这种接口），Mac 之外的用户也受益。
- **Mac 用户的推荐部署**：MongoDB 用 Docker，模型服务和程序本身原生运行。compose 里的 ollama 容器保留给 Linux / Windows 用户。

## 七、结论（2026-10-19 实测）

**Mac 上推荐 Qwen3-4B-Instruct-2507-4bit，用 mlx-lm 原生运行。** 比容器里 CPU 跑的 qwen2.5:3b 快（约 3 秒 vs 4–6 秒）、不占 CPU，中英文 F1 都从八十多提到 96.8%（精确率 93.8%、召回率 100%）。剩下的判错里，两条是把「向大家征集点子」和「技术讨论评论」当成了需求（3b 也错），其余是把科幻类需求判成「非需求」而不是「需求但做不了」，不影响清单。

速度估算和实测对比：估算 4B 每条 3–4 秒，实测约 3 秒，第二节的公式够用。

项目已支持：`docker-compose.mac-gpu.yml` 覆盖文件（模型在宿主机，容器只跑 MongoDB 和 app，已端到端实跑），`local/<模型>` provider 接任意 OpenAI 兼容服务。Linux / Windows 用户继续用容器里的 Ollama。

两段式（小模型跑全量、27B 每周复核）暂不需要：4B 的精确率已经 93.8%。
