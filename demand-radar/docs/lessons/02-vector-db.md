# 第二课：向量库（Qdrant）

## 目标
1. 知道向量库在解决什么问题：**近似索引**（HNSW）、**带过滤的相似度检索**、规模。
2. 自己量出「暴力检索」和「向量库」的交叉点，而不是凭印象。
3. 学会把向量库当成 **派生索引** 来用：MongoDB 是唯一的数据来源，Qdrant 丢了能重建。

## 先说结论（本项目的数据量下）
**不需要向量库。** 我们的库只有几百到几千条，纯 Python 暴力检索 10–30 毫秒。这一课不是为了让你装上它，
而是让你看清它**什么时候才值得**，以及接入它要付出什么（一个服务、一份要同步的索引、一套会过期的数据）。

## 运行
```bash
# 1. 起 Qdrant（可选的 compose profile，默认不启动，app 也不依赖它）
docker compose --profile qdrant up -d qdrant        # 网页控制台 http://127.0.0.1:6333/dashboard
# 2. 镜像里要带客户端（默认不带，镜像大小和以前一样；带上约 +130MB）
DR_WITH_QDRANT=1 docker compose build app
# 3. 把 MongoDB 里的向量同步进 Qdrant（幂等，可重复运行）
docker compose run --rm app index
# 4. 用 Qdrant 检索——和第一课同一条命令，只多一个参数
docker compose run --rm app search "能追踪快递包裹的工具" --retriever qdrant
```
选了 `--retriever qdrant` 但 Qdrant 没起或没建索引，会直接报错并告诉你怎么做，**不会悄悄退回暴力检索**——那会掩盖「你以为在用向量库、其实没有」。

## 设计上的几个决定（每条都值得讲）
| 决定 | 为什么 |
|---|---|
| MongoDB 是唯一来源，Qdrant 是派生索引 | 丢了用 `index --rebuild` 重建；两边不会「谁对」 |
| 点 ID 用 `uuid5(需求 id)` | Qdrant 只收无符号整数或 UUID，而我们的 id 形如 `reddit/x:t3_1`；确定性 UUID 让重复 index 幂等，原 id 放 payload |
| 榜单、领域、来源、时间、可信度放 payload，**并建 payload 索引** | 过滤在 Qdrant 里做；过滤字段不建索引，数据一多就退化成全量扫描 |
| 距离用 Cosine | 分数和暴力检索同一量纲，0.7 / 0.55 的相关度标签才通用 |
| 同一簇只留一条：`group_by(group_key)` | 先取 k 条再去重会少于 k 条；没有簇的需求 `group_key` 就是它自己的 id |
| 显示内容回 MongoDB 取，命中后再核对「仍然入选」 | 索引会过期（需求被转去待确认、簇变了）；待确认的需求永远不能被检索到 |
| 一个嵌入模型一个集合 | 不同模型的向量不能混比，维度也可能不同 |
| 不在 `run` / `schedule` 里自动同步 | 默认行为不变；要 Qdrant 就手动 `index` |

## 怎么保证两个后端一致
`tests/test_qdrant_parity.py`：同一批数据、同一个假嵌入，两个后端必须返回**相同的 id、相同的顺序、相近的分数**，
覆盖榜单、领域、来源、天数、相似度下限、可信度、簇去重、待确认、别的模型的向量、没有向量、索引过期等 16 种情况。
测试用 `QdrantClient(":memory:")`（进程内，不需要服务）。注意它是**精确检索**，不建 HNSW，所以验证的是「接口约定一致」，
近似索引的召回率看下面的基准。

我们还在真实数据上对比过：4 条查询，两个后端的 id、顺序都相同，分数一致。

## 基准：暴力检索到多大才不够用？
```bash
python bench/vector_bench.py                        # 默认 1k / 10k / 100k，约 30 秒
python bench/vector_bench.py --sizes 1000,10000     # 只跑小的
```
需要 numpy 和 qdrant-client（`pip install 'demand-radar[qdrant]'`）。数据是合成的高斯混合，用完自动删。
超过 20 万条要加 `--allow-large`（100 万 × 1024 维约 4GB 内存，先想清楚）。

下面是 2026-10-28 在一台 Mac（Docker Desktop，8 核 / 15.6GB）上跑出来的一次结果：

Qdrant 1.19.2 · 维度 1024 · k=10 · 每个数据量 100 条查询 · 耗时单位 ms（中位数）

| N | 纯 Python | numpy 精确 | Qdrant HNSW 往返 | HNSW 服务端 | Qdrant exact 服务端 | recall@k | 建了索引的向量 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 3.40 | 0.02 | 12.86 | 0.48 | 0.29 | 1.000 | 0 / 1,000 |
| 10,000 | 32.46 | 0.57 | 16.12 | 1.75 | 1.85 | 1.000 | 5,024 / 10,000 |
| 100,000 | ≈328.58（外推） | 5.67 | 16.61 | 1.09 | 6.46 | 0.999 | 100,000 / 100,000 |

纯 Python 一栏每个数据量只测 5 条查询；N 超过 20,000 的标「外推」：在前 20,000 条上实测后按线性放大，是估算，不是实测。
空请求往返（HTTP 自身开销，中位数）：9.46 ms。上传耗时：1,000 条 0.1s，10,000 条 0.9s，100,000 条 10.0s。
「建了索引的向量」为 0 表示这个规模下 Qdrant 没建 HNSW，查询其实是全量扫描。

### 怎么读这张表（比数字本身重要）
- **纯 Python 就是我们现在的暴力检索。** 1 千条 3.4ms，1 万条 32ms，10 万条约 330ms（外推）。线性增长，一眼能看出来。
  我们的数据量在 1 千到 1 万之间，所以**现在完全够用**。
- **Qdrant 的「往返」几乎不随 N 变化**（13–17ms），因为里面约 9.5ms 是空请求的 HTTP 开销（Docker Desktop 的端口转发）。
  小数据量时直接拿它和 numpy 比会冤枉它——要看「服务端」那一列。
- **HNSW 的好处在 10 万条才显出来**：服务端 1.09ms，对比同一个服务做全量扫描（exact）的 6.46ms，约快 6 倍；
  1 千和 1 万条时两者没有差别。
- **「建了索引的向量」是关键。** 1 千条时为 0：Qdrant 在这个规模下**根本没建 HNSW**，查询其实是全量扫描；
  1 万条时只建了一半；10 万条才全建。所以小数据量下「用了向量库」不等于「用了 HNSW」。
- **召回率 0.999**：近似索引用不到 0.1% 的召回换来延迟。但这是**合成的、聚簇结构很干净的数据**，真实嵌入上可能更差。
- **端到端 numpy（5.7ms）在 10 万条时仍比 Qdrant 往返（16.6ms）快**：向量在本机内存里没有网络。
  向量库的价值不只是单次查询快，还有数据放不进一台机器的内存、多个服务共享一份索引、边写边查、复杂过滤。

### 这张表**不能**说明什么（诚实的局限）
- 合成数据，不是真实嵌入；绝对数字只在这台机器上有意义，要看趋势和交叉点。
- 纯 Python 在 10 万条那一行是**外推**（在前 2 万条上实测后线性放大），不是实测。
- numpy 和纯 Python 的计时**不包括从 MongoDB 读向量**。而我们真实的暴力检索路径每次查询都要先读出所有候选的向量
  （5 千条约 40MB），所以真实情况比表里的「纯 Python」更慢；这部分没量，留作练习。
- 单次运行，没有重复取均值；numpy 用了多线程的 BLAS，纯 Python 是单线程。

## 要看出来的几件事
1. 向量库**不是**「RAG 必装」。在你的数据量下，它可能一点好处都没有，还多了一个服务和一份会过期的索引。
2. 它真正解决的是：**规模**（线性变对数）、**带过滤的检索**、**数据放不进内存**。
3. 近似索引是**用召回率换延迟**，不是免费的午餐。
4. 索引要自己维护。需求变了、簇变了、被转去待确认了，索引都会过期——这是任何派生索引的代价。

## 练习
1. 跑一遍基准，在你的机器上找出交叉点。把 `--sizes` 改成 `5000,20000,50000`，HNSW 在哪个规模开始真正建索引？
2. 给基准加上「从 MongoDB 读向量」的耗时，重新比较暴力检索。
3. 在 `QdrantRetriever._filter` 里去掉某个 payload 索引（`ensure_collection`），用 10 万条再测带过滤的查询，慢多少？
4. 手动改一条需求的 `review_cue`（转去待确认），不重新 `index`，检索会怎样？结果里的提示说了什么？
5. 把 `hnsw_ef`（查询时的搜索宽度）调大调小，recall 和延迟怎么变？

## 现状的一个限制
真实库里目前只有 47 条需求带向量（另有 9 条入选的还没有），因为定时任务的 `DR_CLUSTER=0`，新入库的需求不会生成向量。
所以 Qdrant 索引也只有这 47 条。基准用合成数据，不受影响。要让真实数据都能检索，需要 `DR_CLUSTER=1` 或手动跑 `cluster`。
