# 需求雷达：技术路线规划

更新：2026-10-19。路线图（做什么、为什么）见 [`../ROADMAP.md`](../ROADMAP.md)；本文件讲怎么做：架构怎么演进、每个版本改哪些模块、数据结构怎么变、怎么验收。

## 一、规划依据

1. **市场调研的结论：先发布、再加功能**（[`market.md`](market.md)）。需求是真实的，但这类工具能不能吸引人还没被验证。所以第一个里程碑是「能拿出去给人用」，而不是功能最全。
2. **差异化不能丢**（[`landscape.md`](landscape.md)）：全本地模型、一条命令部署、质量可量化。任何新功能都不能引入必须付费的 API、不能增加部署步骤、必须能过评测。
3. **评测基线**：qwen2.5:3b、温度 0，45 条标注样本上 F1 = 85.1%，结果可复现。所有改动以它为准。

## 二、现状与问题

现在的流程（`cli.run`，约 770 行代码）：

```
抓取全部源 → 逐条：已存在就跳过 → 调模型抽取 → 写库 → 查询过滤 → 写 Markdown
```

| 问题 | 影响 |
|---|---|
| 所有内容都要过一次模型 | 慢（3b 每条 7–9 秒）；明显的噪音也要花一次调用 |
| 抽取失败的不入库 | 永远失败的条目每次运行都重试，白白浪费调用 |
| 每次只抓最新 N 条，不记录抓到哪 | 没有积累，历史数据用不上 |
| 可信度几乎都是 0.9 | 排序没有意义 |
| 没有原文摘录 | 无法快速判断模型有没有概括偏 |
| 同一需求在多处出现会重复列出 | 清单冗余，热度被分散 |
| 只有一份全量 Markdown | 不方便定期查看「本周新增了什么」 |

## 三、目标架构

```
                 ┌─────────── sources.toml ───────────┐
抓取（增量游标）→ 规范化 → 规则预过滤 → 模型抽取（并发）→ 入库（带状态）
                                │                              │
                         记录丢弃原因                  ┌──────┴──────┐
                                                   向量化 + 聚类     │
                                                       │            │
                                              排序（分项打分 + 热度）
                                                       │
                                  ┌────────────┬───────┴────────┐
                               全量清单       每周摘要         Web 看板（API）
```

模块划分（括号内为新增或改动）：

| 模块 | 职责 |
|---|---|
| `sources/` | 抓取。**新增**：增量游标、历史回填 |
| `filters.py` | **新增**：规则预过滤，返回丢弃原因 |
| `extract.py` | 模型抽取。**改动**：并发、分项打分、原文摘录、输出语言 |
| `store.py` | 存储。**改动**：条目状态、游标、运行记录 |
| `cluster.py` | **新增**：向量化与相似需求合并 |
| `rank.py` | **新增**：综合排序 |
| `report.py` | 输出。**新增**：每周摘要 |
| `api.py` | **新增**：看板后端 |
| `evaluate.py` | 评测。**改动**：把预过滤算进去；新增摘录、聚类的评测 |

## 四、数据结构演进（MongoDB）

| 集合 | 用途 | 引入版本 |
|---|---|---|
| `demands` | 每条原始内容 + 处理状态 + 抽取结果 | 已有，v0.1 扩展字段 |
| `cursors` | 每个源（每个查询）上次抓到哪 | v0.2 |
| `runs` | 每次运行的统计：各源抓了多少、过滤多少、失败多少、耗时 | v0.2 |
| `clusters` | 合并后的需求：代表描述、成员、总热度、来源数 | v0.3 |

`demands` 新增字段：

```
status          fetched | filtered | extracted | failed
filter_reason   被规则丢弃的原因（如 empty_body、show_hn、product_launch）
attempts        抽取尝试次数，失败超过上限不再重试
excerpt         原文摘录（必须是原文里真实存在的一句）
scores          { clarity: 1-5, intensity: 1-5, feasibility: 1-5 }
schema_version  数据结构版本，方便以后迁移
embedding       向量（v0.3）
cluster_id      所属需求簇（v0.3）
fetched_at / extracted_at
```

**兼容性**：现在还没有正式用户，v0.1 直接加 `schema_version`，旧数据按「未知版本」处理，提供一条重新抽取的命令，不写复杂迁移。

## 五、里程碑

### v0.1：可以发布（约 1.5 周）

目标：拿得出手，能放到 HN、r/SaaS、V2EX 上让人试用，并能定期产出有价值的内容。

**1. 规则预过滤** `filters.py`
- 规则：正文为空或只剩模板内容；`Show HN:` 开头的帖子本身（不含其下评论）；「I made / I built」类自我介绍；正文是 JSON 的机器人内容；Reddit 搜索结果混入的版块简介（id 以 `t5_` 开头）
- 每条规则是一个纯函数，返回丢弃原因或空；规则可以在 `sources.toml` 里逐条关闭
- 被过滤的条目也入库，状态记为 `filtered`，下次不再处理
- 评测：`eval` 先过规则再调模型；报告里加「过滤掉多少条、其中有没有应入选的」。**任何应入选样本被规则误杀即视为不通过**

**2. 抽取结构升级** `models.py`、`extract.py`
- 分项打分：痛点清晰度、表达强度、个人可实现性，各 1–5 分。参考 Reddit_Scrapper 的打分维度
- 原文摘录：让模型从原文里挑一句最能体现需求的话。程序校验它确实是原文的子串，不是就清空，避免模型编造
- 输出语言：新增配置 `output_language`，默认中文；prompt 里写明
- 评测：F1 不能低于 85.1%；新增「摘录有效率」（摘录确实来自原文的比例），目标 ≥ 90%

**3. 失败处理** `store.py`
- 抽取失败也入库，记录 `attempts`；超过 3 次标为 `failed`，不再重试

**4. 综合排序** `rank.py`
- 排序分 = 分项打分加权 + 热度（取对数，避免高赞帖子压倒一切）
- 权重放配置文件里，先给一组默认值，后续根据人工反馈调整

**5. 每周摘要** `report.py`
- 新命令 `digest --days 7`：最近 N 天新增、通过筛选的需求，按领域分组，每条附摘录和原帖链接
- 这是市场验证的工具：每周公开发一份，看有没有人持续关注

**6. 发布准备**
- `docker-compose.yml` 默认模型从 7b 改成 3b，降低配置要求
- 英文 README、LICENSE（建议 MIT，需要你确认）、贡献指南
- GitHub Actions 跑单元测试（评测需要模型，不放进 CI，发版前手动跑）
- 拆成独立仓库

**验收**：
- 评测 F1 ≥ 85.1%，摘录有效率 ≥ 90%，规则零误杀
- 一台干净的机器 `docker compose up` 能出清单和摘要（需要你在本机验证）

### v0.2：持续积累（约 1.5 周）

目标：跑一个月后，库里是几千条有效需求，而不是每天重复处理同样的内容。

**1. 增量抓取** `sources/`
- 每个源（每个查询）记录游标，下次只抓更新的内容：
  - StackExchange：`fromdate` 参数
  - HN Algolia：`numericFilters=created_at_i>游标`
  - GitHub：查询条件加 `created:>日期`
  - RSS：没有游标概念，靠已入库的 id 去重
- 游标存在 `cursors` 集合

**2. 历史回填**
- 新命令 `backfill --source softwarerecs --pages N`：按页往回拉，遵守各源限额（StackExchange 不带 key 每天 300 次）
- 支持中断后继续

**3. 并发抽取** `extract.py`、`cli.py`
- 线程池同时发多个请求，数量可配置（`--workers`，默认 2）
- 写库仍在主线程，避免并发写入问题
- 验收：同一评测集总耗时下降、F1 不变；纯 CPU 上提升可能不明显，以实测为准

**4. 运行记录** `runs` 集合
- 每次运行记一条：各源抓取数、过滤数、抽取数、失败数、耗时。出问题时有据可查

**5. 定时运行**
- compose 里加一个定时服务，每天跑一次 `run`、每周跑一次 `digest`

**6. 技术验证：Arctic Shift**（半天）
- 实测它是否公开可用、条款是否允许、数据是否完整
- 可用的话新增一个 Reddit 数据源，同时解决 RSS 限流和没有历史数据的问题

**验收**：连续运行一周，没有重复处理；回填能中断续跑；运行记录完整。

### v0.3：合并与看板（约 2 周）

**1. 相似需求合并** `cluster.py`
- 向量化：通过 Ollama 跑本地 embedding 模型（候选 `bge-m3`，支持中英文；或 `nomic-embed-text`，更小）
- 合并：先用简单方法（相似度超过阈值就归为一类）；数据量上来、效果不够时再换 sift 用的 UMAP + HDBSCAN
- 合并后热度 = 各条之和，记录来自几个来源
- 几千条规模**不需要向量数据库**：向量存在 MongoDB，计算在内存里做
- 评测：标注一批「这两条是不是同一个需求」的样本，评测合并的准确率

**2. Web 看板** `api.py` + 静态页
- 后端 FastAPI：需求列表（按领域、时间、排序分筛选）、需求簇详情、运行记录
- 前端一个静态页，不引入前端框架
- 放进 docker-compose，起来后浏览器直接打开

**3. 「已有方案」提示**
- 对每个需求簇，查 Product Hunt、GitHub 等，标注「可能已有人做了」
- 先评估能否集成现有的 idea-validation 开源项目，而不是自己重写

**验收**：同一需求在多个来源出现时只显示一条，并标明来源数和总热度；看板能按领域筛选、点开看原帖。

## 六、模型策略

| 用途 | 模型 | 依据 |
|---|---|---|
| 默认 | qwen2.5:3b | F1 85.1%，约 1.9GB，8GB 内存可跑 |
| 低配机器 | qwen2.5:1.5b | F1 78.0%，速度约为 3b 的两倍 |
| 不推荐 | qwen2.5:0.5b | F1 0%，基本不可用 |
| 不推荐 | qwen3:1.7b | 默认开启思考模式，每条 30 多秒，比 3b 还慢 |
| 有 GPU 的机器 | qwen2.5:7b | 未在沙箱实测，需要在真机上评测后再推荐 |
| 向量化（v0.3） | bge-m3 或 nomic-embed-text | 待评测 |

（llama3.2:1b、gemma3:1b 的评测还在进行，结果出来后补充。）

原则：**换模型必须先跑评测**，F1 和速度都写进本表。

## 七、质量保障

- **评测集扩充**：从 45 条扩到 100 条以上，每接入一个新数据源，至少补 10 条该源的标注样本
- **每次改动的门槛**：单元测试全过；评测 F1 不低于基线；有回退就不合并
- **新指标逐步加入**：规则误杀数（v0.1）、摘录有效率（v0.1）、合并准确率（v0.3）
- **CI**：单元测试进 GitHub Actions；评测需要本地模型，发版前手动跑并把结果写进发布说明

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| Reddit 收紧访问（GummySearch 因此关停） | 不依赖单一平台：HN、StackExchange、GitHub 已接入；评估 Arctic Shift；RSS 失败只跳过不中断 |
| 小模型能力天花板 | 规则预过滤减轻模型负担；分项打分让判断更具体；保留切换云模型的能力（可选，不作为默认） |
| 评测集太小，指标有偏差 | 持续扩充，覆盖各个数据源 |
| 范围蔓延 | v0.1 只做发布必需的功能；看板、聚类等放到验证出真实需求之后 |
| 部署门槛（有人不愿意用 Docker） | 保留不用 Docker 的本地运行方式，README 写清楚两种 |

## 九、需要你决定的事

1. **开源协议**：建议 MIT（同类项目大多是 MIT，最宽松）。
2. **输出语言**：默认中文，还是跟原帖语言保持一致？如果要面向海外社区发布，可能需要英文。
3. **独立仓库的名字**：现在叫 demand-radar，发布前可以再想想。
