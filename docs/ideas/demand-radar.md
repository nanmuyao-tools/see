# 想法：需求雷达（给独立开发者的需求发现工具）

> 状态：构思阶段。独立于「短视频时长统计」和「Mac 截图工具」的新想法。

## 一句话

爬取各社区里用户对 App / 工具的**吐槽和许愿**，用大模型把零散评论归纳成结构化的「需求」，排序后供想做独立项目的人快速发现真实痛点。

## 缘起

想做点能解决真实问题的东西，但「做什么」本身就是最难的一步。网上其实有大量现成的需求信号——用户在各处吐槽现有工具难用、许愿「谁来做个 X」。问题是这些信号零散、淹没在噪音里。把它们**自动收集 + 归纳 + 排序**，就能变成一座给独立开发者用的「需求矿」。这个工具本身也是一个对社区有用的开源项目。

## 技术栈契合度

全落在后端 + 数据处理 + LLM，不需要学新语言，也不碰设备 / 隐私 / 流量那些坑。

## 架构

```
数据源（优先官方 API）
  → 抓取层：按源适配，拉评论 / 帖子
  → 原始库：PostgreSQL / SQLite 存原文 + 元数据（来源、链接、时间、点赞数）
  → 抽取层：每条丢给 LLM，输出结构化 JSON
       {需求一句话, 所属领域, 现有方案痛点, 情绪强度, 是否可做成产品}
  → 归并层：embedding + 聚类，或 LLM 归类，把相似需求合并
  → 展示层：按「出现频次 × 情绪强度」排序的需求清单（Markdown / Web 看板），每条附原帖链接
```

## 数据源清单

| 源 | 获取方式 | 信噪比 |
|---|---|---|
| r/SomebodyMakeThis | Reddit 官方 API（PRAW） | 高（本身就是「求做某物」） |
| r/AppIdeas、r/software、r/selfhosted | Reddit API | 中高 |
| Hacker News「Ask HN」 | 官方 API | 高（提问者技术水平高） |
| V2EX「分享创造 / 问与答」 | 官方 API | 中高 |
| App Store 差评 | RSS 评论源 | 中（需过滤「卡 / 广告多」类噪音） |
| 少数派、小众软件、酷安评论区 | 常规爬取（守 robots.txt） | 中 |

## 语义分析：直接用 LLM，不训练模型

不用传统情感分析 / BERT 微调。直接给大模型一段评论、按固定 schema 让它抽出「抱怨点 / 想要的功能 / 领域 / 是否可做」。效果更好、无需训练。不想花 API 费用可用本地开源模型。这反而让项目更简单。

## 真正的难点（技术之外）

1. **信噪比是成败关键**。绝大多数吐槽是「卡、广告多、客服差」，不是能做成产品的需求。有价值的「我需要一个能做 X 的工具」占比很低。项目价值 = 能否把这 5% 筛出来，而非抓得多。
2. **合规与伦理**：
   - 有官方 API 的优先走 API（Reddit、HN、V2EX、App Store），不硬爬。
   - 尊重 robots.txt 与各站服务条款，控制频率，不增加对方负担。
   - 存储 / 展示用户评论涉及版权与隐私：公开版只展示**归纳后的需求 + 原帖链接**，不整段转载原始评论。
   - 不抓取登录后才可见的内容，不绕过反爬限制。

## MVP（先验证「能不能捞出有用需求」）

不要一上来做全自动大平台。先做最小闭环：

```
选 1 个信噪比最高的源（r/SomebodyMakeThis）
  → 官方 API 拉最近 N 条帖子
  → 每条丢 LLM，抽成 {需求, 领域, 痛点, 热度, 是否可做}
  → 存库 + 去重归并
  → 输出一份按热度排序的 Markdown / 网页清单
```

一周能跑通。判断标准：**自己看这份清单，是否觉得「这些点子真能做」**。
- 是 → 逐步加源、加聚类、加看板。
- 否 → 早调整思路，比闷头做半年强。

## 为什么这个方向值得做

- **本身是开源作品**：「独立开发者需求发现工具」，对社区有用，能攒 star。
- **自我造血**：它筛出的需求清单，就是你下一个项目的来源，一箭双雕。
- **无硬性红线**：只要走 API、只展示归纳结果，没有之前几个想法里的隐私 / 伦理问题，可以放心做公开、做大。

## 里程碑
