# 方向调整：按流量行为识别"视频流"

前面的方案靠域名（SNI / DNS）识别 App，有三个难点：

1. 规则要自己维护；
2. HTTPDNS、QUIC、ECH 会削弱识别效果；
3. 私有传输协议可能让方案直接失效。

换一个思路：**不管是哪个 App，只看流量"长得像不像在看视频"。**

## 1. 视频流量的行为特征

内容加密了，但流量的"形状"藏不住：

| 特征 | 看视频 | 刷网页 / 聊天 | 下载文件 / 更新 App | 视频通话 | 听音乐 |
|---|---|---|---|---|---|
| 下行速率 | 持续中高（0.5–5 Mbps） | 低，零星 | 很高，跑满带宽 | 中 | 低（< 0.3 Mbps） |
| 下行 / 上行 | 很高（> 20:1） | 中 | 很高 | **接近 1:1** | 高 |
| 时间形态 | **一阵一阵的突发（ON-OFF）** | 零散 | 连续不断 | 连续平稳 | 稀疏 |
| 包大小 | 下行大多是满 MTU 的大包 | 混杂 | 满 MTU | 中等，较均匀 | 大包，但很少 |
| 持续时间 | 几分钟到几小时 | 短 | 一次性，跑完就结束 | 中长 | 长 |

**短视频和长视频也能分开：**

- **短视频**：每划一下就来一次突发，下一条视频加上预加载，几 MB。突发之间隔几秒到几十秒，**间隔不规则**（取决于人什么时候划）。
- **长视频 / 直播**：自适应码率分片下载，每 2–10 秒一块，**块大小和间隔都很规律**。

## 2. 这条路的优点

- **不需要识别 App，也不用维护域名规则。**
- **不怕 HTTPDNS、QUIC、ECH、私有协议。** 只要流量经过路由器就能看到形状。前一版方案里"一票否决"的风险没了。
- **数据需求很少。** 只要每台设备每 5–10 秒的上下行字节数和包数，最多再加一个包大小直方图。连接表计数（nlbwmon 那套）就能拿到，不用 DPI，也不用解密。
- **路由器几乎没有负担。**

## 3. 代价

- **不知道是哪个 App。** 只能得出"这台手机在看视频"，分不清抖音和 B站。
- **会和这些情况混淆**：长视频、直播、大文件下载、视频通话。前三种靠时间形态区分，视频通话靠上下行比例区分，具体能分得多清楚要实测。
- **最终精度要靠实测数据校准。**

如果你的目标是"控制手机上看视频的总时长"，不区分 App 其实就够用了。手机上的视频时长，大部分本来就是短视频。

## 4. 实现方案（分层推进）

```
每台设备的流量时间序列（每 5–10 秒采样一次：下行/上行字节、包数、连接数）
        │
        ▼
第 1 层：规则判定（立刻可用）
  每分钟：下行 ≥ 阈值  且  下行/上行 ≥ 10  且  不是"长时间跑满带宽"
        → 这一分钟算"看视频"
        │
        ▼
第 2 层：区分短视频和长视频
  看突发的大小和间隔：间隔不规则、每次几 MB → 短视频；规律分片 → 长视频
        │
        ▼
第 3 层（可选）：小模型
  用实测并标注过的数据，训练随机森林或梯度提升树（几十个窗口特征），模型小，路由器上也能跑
        │
        ▼
会话合并（空闲 ≤ 2 分钟）→ 每日时长、超时提醒或拦截

（可选增强）能拿到 SNI 或 DNS 时，顺手标上 App 名，但不依赖它
```

## 5. 数据从哪来

| 来源 | 粒度 | 要求 |
|---|---|---|
| conntrack 计数（nlbwmon 方式） | 每条连接的字节数和包数，每 5–10 秒读一次 | OpenWrt，打开 `nf_conntrack_acct`，关掉 flow offload |
| nftables 按 MAC 计数 | 每台设备的字节数和包数 | OpenWrt，最简单 |
| pcap 只截包头 | 每个包的大小和时间 | 能拿到最细的特征，CPU 占用稍高 |

**硬件仍然需要一台能刷 OpenWrt 的路由器。** 原厂固件拿不到这些数据。

## 6. 验证实验（比之前简单）

抓包的方法不变，但只看流量形状，不用分析域名：

1. 分别录下每种场景各 10–15 分钟：刷抖音 / 快手、看 B站长视频、看直播、刷网页 / 微信聊天、下载大文件、视频通话。
2. 画出每种场景的"下行速率 – 时间"曲线，直观看能不能分开。
3. 用第 1 层规则计算每分钟的判定结果，和真实场景对比，算准确率。

**Go 的标准**："看视频 vs 不看视频"的分钟级准确率 ≥ 90%。
