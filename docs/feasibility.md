# 方向与可行性分析

目标：通过家里的网络，统计自己每天刷短视频（抖音、快手、B站、视频号、小红书）的时长，最好还能在超时后限制使用。

调研细节见 [research/README.md](research/README.md)。

## 1. 先回答一个根本问题：为什么不用手机自带的"屏幕使用时间"？

| | 手机自带（iOS 屏幕使用时间 / Android 数字健康） | 路由器方案 |
|---|---|---|
| 精度 | 精确到 App 前台时长 | 估算，预计误差 10–20% |
| 成本 | 零 | 一台能刷 OpenWrt 的路由器，外加开发 |
| 覆盖 | 只覆盖这一台手机，Wi-Fi 和 4G 都算 | 家里所有设备（手机、平板、电视），但 4G 统计不到 |
| 能否绕过 | 自己设了密码也能自己改 | 不碰路由器就绕不过，"自控"效果更强 |
| 拦截 | App 限额，可以一键"再给 15 分钟" | 网络层拦截，摩擦更大 |

**结论**：如果只是想知道自己刷了多久，手机自带功能更准，而且免费。路由器方案的价值在于：

1. 多台设备一起管；
2. 手机上做不了的强约束，比如晚上 11 点后断开视频 CDN；
3. 统计和规则跟着网络走，不依赖某台设备的设置；
4. 有学习和折腾的乐趣。

这几点值得做，但要清楚它不是"更准的屏幕使用时间"。

## 2. 三个候选方向

| 方向 | 描述 | 可行性 | 结论 |
|---|---|---|---|
| A. 个人工具 | 一台 OpenWrt 路由器（替换主路由，或者接在原路由器后面当专用 Wi-Fi），跑我们写的统计程序 | **高**。技术路线都有开源先例 | **推荐** |
| B. 通用产品 | 支持华为、小米等各种原厂路由器 | **低**。原厂固件封闭、没有接口，一个型号一个样 | 放弃；真要做产品，只能卖自有硬件或固件 |
| C. 手机 DNS | 不用路由器，手机设置私人 DNS，指向自建的 DNS 服务 | **中**。能覆盖 4G，但只有 DNS 信号，HTTPDNS 会漏 | 备选；也可以作为 A 的补充 |

下面重点分析方向 A。

## 3. 方向 A 的技术可行性

### 3.1 能不能识别出是哪个 App？

| 信号 | 可行性 | 依据 / 风险 |
|---|---|---|
| TLS SNI | 高 | TLS 1.3 的 SNI 仍是明文；国内 App 基本没有部署 ECH |
| QUIC SNI | 高 | Initial 包的密钥是公开派生的，nDPI 已经实现了解密，可以移植 |
| DNS 反查 | 中 | 抖音、快手大量使用 HTTPDNS，会漏判；可以试试屏蔽 HTTPDNS 服务，逼它回落到系统 DNS |
| IP 段 | 低 | 字节、快手大量用公共 CDN，只能兜底 |
| **私有传输协议** | **未知（最大风险）** | 字节、快手可能有自研的 UDP 传输或直连 IP，既没有 SNI 也不查 DNS。必须实测 |

**判断**：只要主要的视频流量走标准的 TLS 或 QUIC，识别就可行。私有协议是唯一可能"一票否决"的风险，第一步就要用实测排除。

### 3.2 能不能算准时长？

- **难点一：预加载。** 短视频会提前下载后面几条，所以下载量和观看时长不成正比。
- **难点二：后台保活。** App 切到后台后，仍可能有少量流量。

**对策**：

- 不用"流量 ÷ 码率"来换算，而是按"活跃分钟"计时：某一分钟里下行超过阈值，这一分钟就算在看；
- 再做会话合并：空闲不超过 2 分钟算同一次会话。

**预期精度**：和屏幕使用时间对比，误差 10–20%。阈值要拿真值数据来校准，这一点要实测验证。

区分"刷视频"和"在 App 里聊天、看图"会比较难。第一期统一算作"使用该 App"。视频号和微信聊天必须靠细粒度域名才能区分开。

### 3.3 路由器跑得动吗？

- **v0 方案**（DNS 日志 + conntrack 计数，用户态程序）：资源占用极小，任何能刷 OpenWrt 的路由器都能跑。
- **v1 方案**（加 SNI 提取，每条连接只看前几个包）：参考 nDPI 每流不超过 1.4KB 内存，家庭规模（几千条流）下需要几 MB。可行。
- **注意 flow offload**：开启加速后连接计数会失真，要关掉。千兆满速下 CPU 占用会上升，家用场景可以接受。

### 3.4 硬件门槛

- 需要一台能刷 OpenWrt 的路由器，比如小米 AX3000T 这一档，一两百元。具体型号要查最新的刷机支持。
- 不想动主路由的话，可以接在原路由器后面，开一个"视频 Wi-Fi"，只让手机连它。

## 4. 覆盖盲区（不可消除，只能接受或缓解）

| 盲区 | 影响 | 缓解办法 |
|---|---|---|
| 4G/5G 流量 | 出门或者关掉 Wi-Fi 后完全统计不到 | 手机上关掉这些 App 的移动数据权限；或者叠加方向 C |
| 私有 MAC 地址 | 换了 MAC 设备就认不出来 | 同一个 Wi-Fi 下私有 MAC 通常是固定的；在路由器里绑定静态 IP |
| 未来 ECH 普及 | SNI 失效 | 回落到 DNS 反查和 IP 段，精度会下降 |
| 主动绕过（VPN、代理） | 完全看不到 | 自我管理的场景下可以接受 |

## 5. 工作量估计（方向 A，个人项目）

| 阶段 | 内容 | 估计 |
|---|---|---|
| 0. 实测验证 | 抓手机流量，回答 §6 的问题 | 1–2 天 |
| v0 | DNS 日志 + conntrack + 分钟统计 + 会话合并 + SQLite + 简单网页 | 1–2 周 |
| v1 | SNI 提取（TLS + QUIC），用 NFQUEUE 或 pcap 只看每条连接前几个包 | 1–2 周 |
| v2 | 超时拦截、日报推送、规则学习模式 | 1 周 |

## 6. 第一步：低成本验证实验（不用买硬件）

在电脑上开热点让手机连接，或者用电脑做网关，用 tcpdump/tshark 抓包。每个 App 认真刷 10–15 分钟，同时记下真实的观看时段。要回答这几个问题：

1. **SNI 可见率**：视频下行流量里，有多大比例落在能拿到 SNI 的 TLS/QUIC 连接上？
2. **私有协议**：有没有大流量的 UDP 或 TCP 连接，既不是 TLS 也不是 QUIC，且没有对应的 DNS 查询？
3. **HTTPDNS 比例**：有多少视频连接的目的 IP 在系统 DNS 应答里找不到？屏蔽已知的 HTTPDNS 服务后，App 是否还能正常用、是否回落到系统 DNS？
4. **QUIC 占比**：视频流量中走 QUIC 的比例有多大。
5. **时长关联**：按"活跃分钟"算法得出的时长，和记录的真实时长差多少？刷视频和停留在其他页面时，流量能不能区分开？

**判定标准（Go / No-go）**：

- **Go**：SNI 加 DNS 能覆盖 80% 以上的视频流量，而且时长误差在 20% 以内 → 进入 v0/v1 开发。
- **调整**：主要靠 SNI 才能覆盖 → 直接做 v1，跳过只用 DNS 的 v0。
- **No-go**：大部分视频流量走私有协议，而且只能靠 IP 段识别 → 方向 A 精度不够，改成"手机自带统计 + 路由器只做拦截"。

## 7. 结论

- **方向 A（个人 OpenWrt 工具）技术上可行**。识别、流量统计、存储都有成熟的开源做法可以借鉴，硬件门槛低。
- **最大的不确定性是国内 App 有没有用私有传输协议**，其次是时长阈值怎么校准。两者都能通过 1–2 天的抓包实验确认。
- **建议先做实验，再写主体代码。** 我们可以先写一个分析抓包文件的脚本：输入 pcap，输出上面 5 个问题的答案，作为整个项目的第一个产出。
